# Milestone Report — PV11 (Operations Console)

Date: 2026-07-19 · Track: product validation · Master plan "PV11 — Operations Console",
scoped by the owner's PV11 brief (2026-07-19): "operational rather than consumer-facing…
let an authorized operator inspect and safely act on the validation system without directly
manipulating PostgreSQL… may expose existing backend capabilities, but must not introduce
new financial semantics… avoid turning PV11 into a broad internal admin platform." Exit
gate: "Every mock financial event can be inspected and explained by an operator" — verified
below with a real browser driving a real production build against the real local backend.

## Scope, held to deliberately

The owner's brief named exactly what to cover: vink search/inspection, organizer/participant
state, contribution/ledger visibility, card/purchase status, deadline/recovery state,
outbox/realtime delivery status, refund inspection, safe simulation controls for the pilot,
audit history for every operator action. This report tracks each:

| Named requirement | Delivered as |
|---|---|
| Vink search and inspection | `GET /internal/ops/vinks` (search), one detail page |
| Organizer/participant state | `organizer` + `participants` in the detail response |
| Contribution/ledger visibility | `contributions` + `ledgerEntries` (joined across all 3 `reference_type`s a posting can have) |
| Card/purchase status | `card` + `purchaseAuthorizations` + `settlements` |
| Deadline/recovery state | `recoveryObligations`; deadlines are visible on the vink row itself |
| Refund inspection | refund status lives on `contributions.status`/`refunded_amount_minor` (no separate refund table — PV5/PV7 design), shown in the contributions table |
| Outbox/realtime delivery status | `outboxEvents`, including `published_at` (null = undelivered) |
| Safe simulation controls for the pilot | merchant-authorization + capture — the two actions with no real-world equivalent operators will need during PV12 (see below) |
| Audit history for every operator action | new `operator_audit_log` table, written on every mutating ops action, shown per-vink |

Deliberately **not** built: run-deadlines/resolve-pending action buttons (the deadline sweep
already handles these automatically in production-shaped fashion; forcing them isn't
something a PV12 pilot operator routinely needs — the existing `/internal/simulator/*`
endpoints still cover it for testing), per-operator accounts/roles, a settings/config UI, or
any second view beyond search + one detail page. "Build only what is necessary to diagnose
and operate PV12" was the standing instruction throughout.

## What was implemented

**Backend** (`apps/api/src/modules/ops/`, `auth/operator-tokens.ts`, migration
`0007_operator_audit_log.sql`):
- **D17 (decision log): operator identity is a shared credential, not per-operator
  accounts.** An operator logs in with a free-text name + `env.OPERATOR_PASSWORD`
  (`POST /internal/ops/auth/login`); success mints an 8-hour signed token
  (`typ: 'operator'`, distinct from regular user JWTs so neither is usable as the other).
  Every audit row names the operator by their typed name. Reasoning, alternatives
  considered, and the revisit trigger (a real multi-operator PV12 pilot) are in the decision
  log — this is exactly the "don't build a broad admin platform" call made concrete.
- Every `/internal/ops/*` route is gated by the **same environment allowlist** the PV6
  simulator surface already uses (`simulatorRoutesPermitted` — development/test/demo only)
  **plus** the operator token, checked independently.
- **Read layer** (`ops/store.ts`): `searchVinks` (public code / organizer username / state
  filters) and `getVinkDetail` — one vink, nine parallel queries across every table it can
  touch, deliberately NOT routed through the existing `VinkReader` port (shaped for command
  preconditions and organizer-scoped snapshots, not this wider inspection view).
- **Action layer**: `POST /internal/ops/vinks/:vinkId/merchant-authorizations` and
  `POST /internal/ops/authorizations/:id/capture` call the **exact same application commands**
  (`authorizeMerchantPurchaseCommand`, `settlePurchaseCommand`) the PV6 simulator routes
  call — copied glue, not new logic — satisfying "must not introduce new financial
  semantics" literally. Both write an audit row on success.
- CORS extended to a second allowed origin (`OPERATIONS_CONSOLE_BASE_URL`, alongside PV10's
  `VINKIN_PUBLIC_BASE_URL`).

**Frontend** (`apps/operations-console/`, Next.js — matching apps/guest-web's PV10 stack):
login gate (`localStorage`-held operator session, same documented tradeoff as PV10's guest
session), a search page, and one detail page with nine inspection sections plus the two
action forms and the per-vink audit log. `components/DataTable.tsx` renders raw DB rows
generically (columns = union of keys present) rather than a bespoke component per table —
the concrete expression of "don't build a broad admin platform": one generic table renderer
covers nine different shapes.

## A real bug found and fixed by end-to-end testing

The Capture form's "Settlement: MATCHED" confirmation never appeared, even though the
backend genuinely completed the settlement correctly every time (confirmed directly via
`curl` against `/internal/ops/vinks/:id` mid-investigation — the vink really did reach
COMPLETED). Root cause: the form was keyed on the open authorization's id
(`key={openAuthorization?.id}`, added to satisfy a `react-hooks/set-state-in-effect` lint
rule) so that it would reset cleanly when a new authorization appeared — but capturing an
authorization changes its own status from `APPROVED` to `CAPTURED`, which makes
`openAuthorization` become `undefined` in the very same refetch that was supposed to let the
operator see the success message. The key changed, React unmounted and remounted the form,
and the mutation's own success state was destroyed a moment after it was set — a real UI bug
masking real, correct backend behavior. Fixed by reverting to a plain `useEffect` for the
one legitimate prop-sync case (with a documented, targeted lint suppression) instead of a
`key`-based remount, so the form's local mutation state survives its own refetch.

A second, smaller bug from the same investigation: the Capture form never sent
`providerAuthorizationId` at all (only `MerchantAuthorizationForm`'s response carried it,
with no shared state to pass it to its sibling). Fixed by reading it back from
`purchaseAuthorizations[].provider_authorization_id` in the already-fetched vink detail
instead of threading it through component state.

## Database changes

New migration `0007_operator_audit_log.sql`: one table, `operator_audit_log` (operator
name, action, optional vink id, JSON details, timestamp) — append-only by convention, no
trigger (unlike the financial ledger, a mistaken audit row has no money-correctness
implication, so the enforcement cost wasn't worth it here).

## APIs added

`POST /internal/ops/auth/login`, `GET /internal/ops/vinks`, `GET /internal/ops/vinks/:vinkId`,
`GET /internal/ops/audit-log`, `POST /internal/ops/vinks/:vinkId/merchant-authorizations`,
`POST /internal/ops/authorizations/:authorizationId/capture` — all environment-gated
(development/test/demo) and operator-token-gated (all but login).

## UI added

The full operations console: login, vink search, one vink detail page (funding, participants,
contributions, card, simulation controls, purchase authorizations, settlements, recovery
obligations, ledger entries, outbox/realtime delivery, state history, audit log).

## Known limitations

1. **Operator identity is a shared password (D17), not accounts** — deliberate, matches the
   "avoid a broad admin platform" instruction; the decision log names PV12 (a real pilot with
   multiple operators on shifts) as the revisit trigger if attribution-by-typed-name proves
   too weak.
2. **Operator session lives in `localStorage`**, same category of tradeoff as PV10's guest
   session — acceptable for a mock-money validation build with a handful of trusted users,
   not for anything closer to real money.
3. No automatic sign-out on token expiry (8-hour TTL) — an expired token surfaces as failed
   requests rather than a redirect back to login. Low-friction to fix, not done here to keep
   this milestone to what the brief actually asked for.
4. Refund inspection is read-only (contributions table), matching the brief's "inspection"
   framing — no refund-retry action button was added since PV7 already has its own retry
   path via the organizer flow and the owner's brief didn't name it as a needed simulation
   control.

## Security review

- Every `/internal/ops/*` route (except login) requires a valid, correctly-typed
  (`typ: 'operator'`) signed token — verified by test that a regular user JWT is rejected
  (401), not silently accepted.
- Environment allowlist unchanged and reused, not weakened: ops routes never register
  outside development/test/demo, identical to the existing simulator surface.
- The two action routes perform zero new financial logic — they call the identical
  application-layer commands already covered by PV6's own tests and contract-test suite;
  this milestone's new tests cover the transport (auth, audit-attribution) layered on top,
  not re-proving settlement correctness.
- `OPERATOR_PASSWORD` follows the same pattern as `JWT_SECRET`: a checked-in dev-only
  default that the `demo` environment (the one PV12 pilot operators actually use) refuses at
  boot, forcing an explicit value there.
