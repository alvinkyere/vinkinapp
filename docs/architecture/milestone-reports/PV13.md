# PV13 — Pilot UX/UI Correction

**Status: substantially complete.** The organizer Flutter app and guest-web were rebuilt on
a real, sourced VinkIn design system and a corrected product flow (organizer contributes
through the same engine as everyone else, unknown usernames offer a guest path instead of a
dead end, split math is exact and organizer-inclusion-aware). The fully scripted exit-gate
journey from the brief passes end-to-end on a real iOS Simulator against the real local
backend. Two things are explicitly **not** done and are called out plainly in "What's left"
below, per the brief's own instruction not to claim completion on tests alone.

## Why this milestone happened

The owner reviewed the PV9 organizer app after PV9–PV12-prep landed and found it
"technically functional but not product-ready": it didn't visually resemble vinkin.org, it
didn't clearly split a bill, it excluded the organizer from contributing, and it treated any
non-member username as a dead end. The brief's own words: "Do not treat this as a collection
of small patches. Rebuild the organizer experience as a coherent VinkIn product." This report
covers that rebuild.

## What was built

**Design system, sourced from the live site, not approximated.** Fetched vinkin.org's raw
compiled CSS/HTML directly (not a summarized description) and wrote
`docs/design/vinkin-design-system.md` — exact hex colors (`ink #0A0A0B`, `paper #F7F3EB`,
`smoke #6E6A61`, `blue #315CFF`, `blue-deep #2247D6`), exact fonts (Bricolage Grotesque
display, Inter body), exact button/card/radius/shadow values, the site's own tone-of-voice
copy, and the exact tagline ("Everyone In. One Purchase." — caught and corrected a wrong
paraphrase mid-build). A full Flutter token system
(`apps/mobile/lib/design_system/{vink_colors,vink_typography,vink_spacing,vink_radius,vink_shadows,vink_theme}.dart`)
and 16 reusable components (buttons, text/money fields, surface card, avatar, participant
row, progress bar, status badge, bottom sheet, app bar, empty/loading/inline-error states,
amount summary, step header, simulation notice, logo) — every button meets the 44×44pt
touch-target minimum, every interactive control has loading/disabled states, every icon has
a semantic label. The app's real `ThemeData` is now wired in (`app/app.dart` →
`buildVinkTheme()`) — it was built earlier in the session but never actually connected until
this pass; the old Material-default theme (`app/theme.dart`) and its entire parallel design
system (`design_system/{colors,typography,spacing}/`, `vinkin_button.dart`, `status_pill.dart`,
`async_state_view.dart`, `simulation_banner.dart`) are deleted, not just superseded — nothing
in the app can silently fall back to generic Flutter blue anymore.

**Navigation.** `go_router`'s `StatefulShellRoute.indexedStack` replaces the flat route list:
persistent Home / Activity / Profile tabs, with `/create-vink` and `/vinks/:id` as top-level
pushed routes above the tab bar. No backend terminology anywhere in navigation.

**Home screen.** Dominant "Start a Vink" CTA; Active Vinks cards (title, funded/required via
the shared progress bar, participant count via a bounded per-vink snapshot fetch, time
remaining, human status label, a state-appropriate next action); every D11 state maps to
warm copy via `vinkStatusLabel()` (`vink_status_badge.dart`) — never a raw backend name; a
recent-activity preview linking to the Activity tab; a real empty state with its own action.

**Create Vink — five steps, matching the brief's own breakdown.** Purpose (category picker —
see "What's left" for why this isn't a freeform name field) → Total (`VinkMoneyField`) → Add
people (organizer auto-included with an explicit "Include me in this Vink" toggle, default
on; "Add someone" opens a bottom sheet that looks up a username and, on `USER_NOT_FOUND`,
**never** says anything like "you have to be a member" — it offers "Add as guest" or "Try
another username" right there; a guest needs only a display name and gets a shareable
`/g/:token` link with Copy/Share/QR) → Split (Equal or Custom only — Percentage is excluded
because the backend doesn't support it; Equal mirrors the backend's own largest-remainder
algorithm exactly via `split_calculator.dart`, organizer-inclusion-aware; Custom has a live
Assigned/Remaining readout and disables Continue until the sum matches exactly; the organizer
can be included, excluded, or given a custom amount — including an explicit, deliberate zero
in Custom mode — never silently zeroed) → Review (full summary, edit links back into People
or Split, "Open Vink").

**Live Vink lobby.** State-specific copy for all 16 D11 states; a card block that says
"PILOT SIMULATION" and is paired with a `VinkSimulationNotice` reading "Pilot simulation — no
real card has been issued, no real money moves" wherever mock money/card state is visible;
Copy/Share/QR sharing of the general join link. The organizer's own **"Pay my $X"** goes
through `POST /contributions/authorize` — the exact same endpoint and code path every other
participant uses (`findOwnParticipant` in `packages/application/src/contributions.ts`
resolves by requester identity with no special-casing for the organizer role) — never a
shortcut, never a hidden default. Per-participant "paid / processing / waiting" status
required a small, deliberate backend addition (see below).

**Guest-web.** Same five colors, same two fonts (via `next/font/google`, mirroring the
Flutter app's own choice), same card shape (`rounded-[2rem]`, the site's own hero-mockup
blueprint), same button shape (`rounded-full`, uppercase, wide-tracked), same status
vocabulary (`StatusBadge.tsx`'s label table mirrors `vink_status_badge.dart`'s exactly), same
"paid stays blue, no invented green" rule. Not converted to Flutter — still Next.js/Tailwind,
per the explicit scope constraint.

## A deliberate, small backend addition

The lobby's per-participant "paid / processing / waiting" status has no existing read path —
`GET /api/v1/vinks/:id` never exposed contribution status per participant. Added one
plain (unlocked) read method, `VinkReader.listContributionsByVink`, implemented in
`PostgresVinkStore` and the in-memory test double, and a `contributions` field on
`VinkSnapshot` (`packages/application/src/queries.ts`) carrying each participant's latest
contribution status. This is additive and read-only — no new tables, no settlement-semantics
change, no D15 impact, nothing that touches the ledger or provider boundary.

## Real defects this pass caught (not just wrote UI for)

Each of these was found by actually running the app against the real backend, not by
inspection:

1. **Two identically-labeled "Start a Vink" buttons** were simultaneously visible on a fresh
   Home screen (the dominant CTA and the Active-Vinks empty-state action) — genuinely
   ambiguous for a screen reader, and it broke `find.text()` in the very first widget test
   that exercised the screen. Fixed by giving the empty-state action its own copy ("Start
   your first Vink").
2. **The category picker offered categories the backend rejects.** `RESTAURANT` is listed in
   the API's own enum but gated behind a `restaurant_variable_policy` flag that's off by
   default (`packages/domain/src/policy.ts`); `HOTEL`/`FUEL`/`CAR_RENTAL` are permanently
   unsupported for MVP. Selecting any of them threw `UNSUPPORTED_PURCHASE_CATEGORY` at
   create time with **no visible error on screen** (see next item) — a silent dead end.
   Fixed by restricting the picker to the three categories the backend actually accepts
   today (`GROCERY`, `RETAIL`, `ELECTRONICS`) — the same "never offer what the backend will
   reject" rule this milestone already applies to the Percentage split method.
3. **The Total step never rendered its own error state.** `_createVinkAndContinue()`'s
   catch block set `_error`, but `_buildTotalStep()` never read it — an API failure (like
   the one above) failed silently with the Continue button just stopping its spinner. Fixed.
4. **The guest-invite bottom sheet overflowed on shorter devices** (`RenderFlex overflowed
   by 2.0 pixels`) — the QR code, link box, and action buttons together were taller than
   `showVinkBottomSheet`'s unbounded `Column`. Fixed by bounding the sheet to 90% of the
   viewport height and wrapping it in `SingleChildScrollView` — applies to every sheet in
   the app, not just this one.

## Verification — what's actually proven, and how

- **Flutter**: `flutter analyze` clean (four pre-existing infos, unrelated to this pass, plus
  three `hasFlag`-deprecation infos in one test file — no errors, no warnings).
  **23/23 unit/widget tests pass**, including new coverage this pass added: every human-copy
  mapping (`purchaseCategoryLabel`, `humanErrorMessage`, `vinkStatusLabel`, `activityCopy`,
  `paymentStateFor`) asserted to never leak a raw backend code/state/event name; accessibility
  checks (`VinkPrimaryButton`'s enabled/disabled semantics, `VinkStatusBadge`'s human label,
  `VinkProgressIndicator`'s funded/required/percent semantics).
- **The fully scripted exit-gate journey passes on a real iOS Simulator against the real
  local backend** (`integration_test/e1_test.dart`, rewritten for the new UI): register →
  create a $120 Vink → Purpose → Total → add an existing member by username → try an unknown
  username and get the guest offer, not a dead end → add the guest, capture their real
  `/g/:token` link → Equal split, organizer included, sees exactly $40.00 × 3 → Review → Open
  → the organizer's own **Pay my $40.00** through the real contribution endpoint → the
  member's and guest's own approvals driven directly against the API (their own UI is
  guest-web's PV10 Playwright scope, not this app's) → live FUNDED with no reload → a real
  card provisioned by the real deadline sweep (no simulator shortcut), clearly labeled → a
  merchant simulation → live COMPLETED with no reload. This single run is what surfaced
  defects 1–4 above.
- **Guest-web**: `tsc --noEmit`, `eslint`, and a production `next build` all clean.
  `tests/e9.spec.ts` (a guest joins and funds their share from a real mobile-viewport browser
  against the real backend, no app install) passes against the restyled UI unchanged in
  substance — only visual classNames moved, no text a `getByRole`/`getByText` selector
  depends on changed.
- **Backend**: 36/36 `packages/application` tests, 63/63 `apps/api` tests including all
  PostgreSQL/Redis integration suites (`VINKIN_INTEGRATION=1`) pass; `pnpm typecheck`,
  `pnpm lint`, `pnpm format:check` (own files), and `pnpm guard` all clean repo-wide.
- **Visual quality gate**: informal — the design doc's audit and every component's sourcing
  comment tie back to specific vinkin.org values, and guest-web's own screenshots (captured
  during the E9 run) were visually reviewed against the site's real palette/type/card
  language. A formal, deliberate side-by-side comparison screenshot set was **not** produced
  this pass (see "What's left").

## What's left (flagged, not hidden)

- **Purpose step has no freeform name/merchant/note field.** The domain has none —
  `createSchema` only carries `purchaseCategory` (an enum), and `configureSchema` can't
  change it after creation either. The brief's "name/merchant/note" framing doesn't map onto
  a real field anywhere in the system. Category selection is the closest real proxy and is
  what got built; adding a freeform title field is a schema change and, per this repo's own
  rule, a product change that needs an owner decision and a migration, not something to add
  silently inside a UX-correction pass.
- **The 13 named screenshots and the explicit side-by-side visual-quality-gate comparison
  were not captured as a deliverable set this pass.** The Simulator run that proved the exit
  gate journey is real and repeatable, but `flutter test -d <device>`'s `takeScreenshot()`
  doesn't persist PNGs without a driver script (`flutter drive` + `integration_test_driver`)
  wiring that up — discovered mid-pass, not fixed within this session's remaining budget.
  guest-web's own screenshots (from `tests/e9.spec.ts`) exist and were reviewed, but the
  Flutter side's 9–10 equivalents (Home, Enter total, Add people, Unknown-username prompt,
  Equal split, Review, Live lobby, Card ready, Completed) are not on disk. Immediate next
  step: wire `integration_test_driver.dart` (or switch to `flutter drive`) so
  `e1_test.dart`'s existing `takeScreenshot()` calls actually write files, then do the
  explicit side-by-side comparison against vinkin.org the brief asks for.
- **Custom-split mismatch scenario (brief's Scenario B) has unit coverage of the underlying
  math but no end-to-end UI proof** that the Continue button stays disabled and the specific
  over/under copy renders correctly on a live device. `VinkAmountSummary`'s copy is unit-
  testable in isolation but wasn't exercised through a full custom-split UI run this pass.
- **`apps/operations-console` was not touched** and its own Playwright suite is unaffected in
  substance — but running the full monorepo `pnpm test` under parallel `turbo` load produced
  a flaky failure in `pv11-exit-gate.spec.ts` waiting on `CARD_READY` (a deadline-sweep
  timing/phase-alignment race under concurrent-suite load against the same shared Postgres,
  the same category of flake the E1 test's own comments already document). Confirmed passing
  in isolation twice; not a regression from this pass, but worth noting since it surfaces
  under `pnpm test`'s default parallelism.

## Explicit scope constraints honored

No real financial provider touched; D15 untouched; no new settlement semantics; no ledger
changes (the one backend addition is a plain read, not a write path); no chat/contacts/admin
features; the realtime architecture (WS signal → refetch authoritative snapshot) is preserved
exactly, including through the live FUNDED/CARD_READY/COMPLETED transitions proven above;
guest-web was not converted to Flutter; Percentage split is not offered; pilot-simulation
status is never hidden (`VinkSimulationNotice` + the card's own "PILOT SIMULATION" label).
