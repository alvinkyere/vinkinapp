# I7 — Live Vink and Ink Progress

**Brief:** the second slice of the owner-directed mockup-gap plan (Invites, then I7, then Home
polish) — `docs/design/phase-10-implementation-readiness.md`'s own `### I7` entry, already
fully speced across four documents (Phase 0 §D20, Phase 4 §0, Phase 6 §12, Phase 8 §15, Phase 9
§10) but 0% built before this slice. Per the owner's own earlier decision (this session, when
first shown the two aspirational mockups): build to the existing, ratified Phase 8 §15 spec — a
calm, smooth level-rise fill, explicitly **not** the mockups' literal liquid-physics animation.

## What shipped

- **`VinkProgressVessel`** (`apps/mobile/lib/design_system/components/vink_progress_vessel.dart`,
  new) — a single component, two variants:
  - **Primary** (Lobby, organizer and participant): headline ("$X of $Y ready"), the vessel
    itself, and an optional waiting clause.
  - **Compact** (Home's active-Vink card): fill only, no headline or waiting-clause text, per
    Phase 8 §15's own table.
  - Driven only by `confirmedAmountMinor`/`totalAmountMinor` (i.e. `contributionProgress`,
    D20/D24) — never `fundedAmountMinor`. Fill animates smoothly between rebuilds
    (`TweenAnimationBuilder`, ~400ms `easeOutCubic`) and respects `MediaQuery.disableAnimations`
    (instant level change under reduced motion, per spec). An empty vessel keeps a small
    decorative sliver visible (not literally zero-height) while the accessible `Semantics.value`
    still reports the real percentage.
  - **Explicitly not a liquid/physics simulation** — no ripple, splash, bubble, or droplet
    rendering, matching Phase 8 §15's own locked rule, restated in the component's own doc
    comment so a future editor doesn't reintroduce it by mistake.
- **Two waiting-clause helpers**, not one, because the two Lobby views have genuinely different
  data available:
  - `organizerWaitingClause` — Phase 6 §12's exact table (0/1/2/3+ unconfirmed names, switching
    from names to a count at three), using real participant names already visible on the
    organizer's own Lobby (D24/D25's organizer-sees-all boundary).
  - `participantSafeWaitingClause` — a disclosed adaptation for the participant/guest privacy-
    scoped view, which structurally only ever has counts (`ParticipantVinkSummary` carries no
    other participant's name). Phase 6 §12's own table assumes name data this view doesn't have;
    rather than silently inventing names or leaving the clause blank, this counts instead.
- **Wired in, replacing `VinkProgressIndicator` entirely** (not alongside it, per Phase 4 §0's
  explicit rule): `vink_lobby_screen.dart`'s organizer body (`_LobbyBody`) and participant body
  (`_ParticipantLobbyBody`), and `home_screen.dart`'s `_ActiveVinkCardV2`. The flag-off legacy
  paths (`_ActiveVinkCard`, both bodies' `else` branch) are untouched, same rollback discipline
  as every prior flagged slice.
- **A real, pre-existing gap found and fixed as a direct consequence of this work**: the
  organizer Lobby's progress bar had been reading raw `vink.fundedAmountMinor` all along — not
  `snapshot.contributionProgress` — meaning it was still exhibiting exactly the "jumps 0→100%"
  problem (P0-3) this slice exists to solve, undetected because nothing had compared the two
  fields on that specific screen before. Now reads `contributionProgress`.
- **Participant-row consolidation** (Phase 8 §13/§27's "duplicate 'Your share' card" note): the
  organizer's own row in the Lobby's "Participants" list is skipped only while the standalone
  "Your share" card (with the actionable Pay button) is also rendered — restored once that card
  disappears (already paid, or the vink isn't `OPEN`), so no information is ever lost, only the
  literal double-render of the same status.
- **Feature flag**: `FeatureFlags.inkProgressVessel` (`--dart-define=INK_PROGRESS_VESSEL=true`),
  default off.

## Tests

- `test/design_system/vink_progress_vessel_test.dart` (new, 14 tests): every Phase 8 §15 fill
  state (empty/partial/complete) with the correct accessible percentage independent of the
  decorative visual floor, the compact variant's own "no text" rule, a reduced-motion render
  proving no exception, and both waiting-clause helpers' full Phase 6 §12 table (including the
  organizer/participant divergence at "3 unconfirmed").
- Full `flutter test` (no path filter): **233/233** green (up from 219), including every
  existing Lobby/Home test unaffected by the flag-off default. `flutter analyze` clean at the
  documented 11-issue baseline.

## Real-device result

`apps/mobile/integration_test/ink_progress_vessel_test.dart` (new), real iOS Simulator, real
local backend, `--dart-define=INK_PROGRESS_VESSEL=true`: an organizer creates and opens an $80
Vink split with `demo_member_1`, confirms their own $40 share, and the Lobby's vessel headline
is observed rising **$0 → $40 → $80** live, without navigating away or refreshing — the direct,
real-device proof that the vessel genuinely reflects incremental per-contribution progress, not
a value that only ever jumps at full resolution. `e1_test.dart` (flag off, default) re-run
clean immediately after, confirming the rollback contract.

## Deviations / disclosed gaps

- **No literal droplet-joining animation on guest success** (Phase 4 §0's fourth placement row)
  and no Phase 9-precise motion timing — Phase 9's own motion-system document was explicitly
  out of this session's scope; the ~400ms `easeOutCubic` choice is a reasonable default, not a
  claim of matching Phase 9's exact specification.
- **Guest Web (`apps/guest-web`) is untouched** — its own vessel is I8's scope, per the phase-10
  entry's own "Guest Web changes: none (that's I8)" line; this slice is `apps/mobile` only.
- **`participantSafeWaitingClause` is a genuine, disclosed departure from Phase 6 §12's literal
  table** (see above) — flagged, not silently worked around.

## Is I7 fully closed?

Yes, for `apps/mobile`. Guest Web's own vessel remains I8's explicit scope, unstarted, matching
the original phase-10 entry — not a gap this slice left behind.
