# Milestone Report — PV10 (Participant/Guest Mobile Experience)

Date: 2026-07-19 · Track: product validation · Master plan §4 "Guest checkout" /
"PV10 — Guest Web Application". Exit gate: "A guest completes E9 on a mobile browser
without installing the app" — verified below with real browser automation (mobile
viewport) against the real local backend, not a mock.

## Scope correction, made explicit before any code changed

The PV9 report's "Next milestone" note assumed PV10 would be more Flutter screens. That
was wrong: the master plan's §4 technology stack section is explicit — **"Use a lightweight
responsive web application rather than forcing Flutter web"** for guest checkout, with a
recommended stack (Next.js, TypeScript, Tailwind CSS, TanStack Query, WebSocket/SSE) and a
named directory (`apps/guest-web/`) distinct from `apps/mobile/`. PV10 is therefore a new
web app, not an extension of the organizer Flutter app. Caught by re-reading the plan before
scaffolding anything, not after.

## What was implemented

**`apps/guest-web/`** — Next.js 16 (App Router) + TypeScript + Tailwind CSS 4 +
TanStack Query, wired into the pnpm workspace and Turborepo (`@vinkin/guest-web`, own
`typecheck`/`lint`/`test` scripts; lints separately from the root `eslint.config.mjs` via
its own Next-aware config, the same split as `apps/mobile`'s `flutter analyze`).

- **Join flow** (`/join/[publicCode]`): pre-join summary (category, total, participant
  count, joinable status) from the existing anonymous `GET /api/v1/join/:publicCode`; a
  join form (display name only, no account) posts to the existing PV4
  `POST /api/v1/public/vinks/:publicCode/participants`.
- **Session view**: the guest's own live view — funding progress, their share, and a
  contribution-approval button wired to the existing PV5
  `POST /api/v1/guest/contributions/authorize`. A returning guest's session persists in
  `localStorage` (flagged below) so reopening the link skips straight back to their session.
- **Live updates**: the guest connects to the *same* `vinkId`-keyed realtime channel PV8
  built for the organizer app — a backend extension, see below.
- **Responsive + accessible**: mobile-first Tailwind layout (verified at an iPhone 13
  viewport); `role="status"`/`role="progressbar"`/`aria-live`/labeled form fields throughout.
- **Signup conversion**: an honest, dismissible informational prompt after a guest
  participates — no fake web registration form (none exists in the product yet; account
  creation is PV9's Flutter app), consistent with the exit gate's "no account creation"
  requirement.

## Backend extensions (small, flagged, all with new tests)

Three real gaps surfaced by actually building the guest client, not anticipated up front:

1. **Realtime channel had no guest-token path.** `GET /api/v1/vinks/:vinkId/live` only
   accepted organizer/participant JWTs (`getVinkSnapshot`, which explicitly rejects any
   caller that isn't the vink's `organizerUserId`). Guests authenticate with a `vgt_`-prefixed
   opaque token (D14), not a JWT. **Fixed**: the route now branches on the `GUEST_TOKEN_PREFIX`
   the REST guest surface already uses — a guest token resolves via
   `store.findGuestParticipant`, is checked against the path's `vinkId`, and gets the
   existing guest-scoped `GuestVinkView` (Plan PV4) as its `snapshot` — never the organizer's
   full `VinkSnapshot` (no card, no other participants). Same event stream, same hub
   subscription; only the snapshot resolution differs.
2. **A joined guest had no way to learn their own vink's id.** `PublicVinkSummary` and
   `GuestVinkView` deliberately carry no internal ids pre-join — but the realtime route is
   keyed by `vinkId`, and a guest genuinely needs it once joined to open that channel.
   **Fixed**: `GuestVinkView.participant` and the join response's `participant` object now
   include `vinkId` (already present on the underlying domain `Participant`, just not
   whitelisted through) — scoped to *after* a genuine join, the anonymous pre-join
   `PublicVinkSummary` is unchanged.
3. **No CORS.** The organizer Flutter app isn't subject to browser CORS; a Next.js app
   fetching a different-origin API is. **Fixed**: `@fastify/cors`, allowing
   `VINKIN_PUBLIC_BASE_URL` — which was already, by design since PV4, "the guest web app's
   own origin" (it's what join links point at) — as the allowed origin. One env var now
   serves both purposes; its dev default moved from a placeholder (`:3000`, the API's own
   port, from before any guest app existed) to guest-web's actual dev port (`:3100`).

## A real defect found and fixed by end-to-end testing

The guest realtime hook initially patched only `state`/`fundedAmountMinor` from live event
messages (the outbox publisher's lean-by-design payload), leaving `participant.
allocatedAmountMinor` stale — **the identical class of bug PV9 found and fixed in the
organizer Flutter app's Lobby screen** (a provisioned card staying invisible there; here, a
newly-assigned share staying at $0 after the organizer re-split). Caught the same way: real
end-to-end testing, not unit tests, since nothing exercises a live *second* state change
after the initial snapshot. **Fixed** with the same pattern PV9 used — re-fetch the full
guest session via REST on every live event, not just patch the two fields the event carries.

## A real environment defect found (not a product bug)

Next.js 16's Turbopack dev server's HMR WebSocket handshake fails in this environment
(`ERR_INVALID_HTTP_RESPONSE`), and — non-obviously — that failure silently prevents client
hydration entirely: `useEffect` never fires, verified directly with a minimal isolated
repro page (`mounted` stayed `false` indefinitely; zero console output from the effect).
Confirmed by elimination it's Turbopack-dev-mode-specific: a production build
(`next build && next start`) hydrates and fires effects correctly, immediately, every time.
**All manual verification and the automated exit-gate test run against a real production
build** (`playwright.config.ts`'s `webServer` runs `npm run build && npm run start`), which
is arguably more representative of the real exit-gate condition than dev mode would have
been. Flagged for whoever next runs `pnpm --filter @vinkin/guest-web dev` on this machine —
it may need `--webpack` or an environment fix; not investigated further since it doesn't
block anything this milestone needs.

- guest-web: `tests/e9.spec.ts` — the actual exit-gate proof, Playwright at a real iPhone 13

## Known limitations

1. **Guest session token lives in `localStorage`, not an httpOnly cookie.** A deliberate
   PV10 simplification, flagged in code (`lib/session-storage.ts`): a guest link with no
   account has nowhere else to keep client-held state, and this is a mock-money validation
   build. Same G4-adjacent territory as the organizer app's JWT-in-URL flag on the realtime
   channel (PV8) — revisit before real money.
2. **No organizer self-approve-contribution UI** (carried over from PV9, unaddressed here):
   the E9 test drives the organizer's re-split directly against the API rather than through
   any UI, since neither app has a screen for it yet. Still flagged for whoever picks up
   that gap.
3. Chromium only for the exit-gate proof (see Tests added) — not a WebKit/Safari-specific
   compatibility proof, though the CSS is standard Tailwind with no Chromium-specific
   features.
4. Next.js dev mode (Turbopack) doesn't hydrate in this environment (see above) — production
   mode is unaffected and is what every verification in this milestone actually used.
5. "Optional signup conversion" is informational only (see above) — no functional web
   registration exists to convert into yet.

## Security review

- Guest tokens are opaque, hashed at rest (D14, unchanged), never logged; the join response
  is the only place the raw token appears, same as PV4.
- The realtime channel's new guest branch performs its own ownership check
  (`resolved.participant.vinkId !== vinkId` → 403) before ever subscribing the socket —
  verified by test, not just inspection.
- CORS is scoped to exactly one configured origin (`VINKIN_PUBLIC_BASE_URL`), not a
  wildcard.
- The `vinkId` now exposed to a joined guest is an opaque UUID with no meaning outside this
  system and is already implicitly known to anyone who could reach the realtime channel as
  that guest in the first place; it was withheld pre-join for a different reason (no
  internal state before consent to join), not as a secrecy boundary post-join.
