# Slice I6 — Home, Activity, and Vink Details

**Brief:** owner-directed, resumed from a paused working tree after an R0 Mobbin research
detour (`docs/design/references/mobbin/00-reference-index.md`,
`docs/design/references/mobbin/i6-home-activity-details.md`). Full scope: redesign Home
(remove the persistent tagline, needs-attention/waiting-on-others sections), redesign Activity
(outcome-summary list, partial-failure resilience), and build a new Vink Details screen — all
grounded in the approved Phase 4/5 contracts and D39–D43, with Mobbin used only as visual
supporting evidence. "Stop after I6."

## Existing paused work: retained, changed, discarded

Of the 39 pending changes present when this session resumed, the ones this slice owns were
inspected before editing, not restarted from scratch:

- **Retained as-is:** the Home header redesign (tagline removal, restrained identity mark +
  Profile access), the two-section attention-bucket classification
  (`organizerAttentionBucket`/`participantAttentionBucket`, including the found-and-fixed
  RESTRICTED-reachability gap), Activity's outcome-summary list and partial-failure resilience
  work, and the general screen scaffolding for Vink Details.
- **Changed:** Home's compact progress bar was wired to `fundedAmountMinor`-derived math in the
  paused draft — corrected to consume the server-projected `contributionProgress` (D20/D24)
  directly, per explicit owner instruction. This required adding a `ContributionProgress` Dart
  model, parsing it out of `VinkSnapshot.fromJson` (a field the server already returned and the
  client silently dropped), and threading it through `ActiveVink`/`home_providers.dart`.
- **Discarded and rebuilt:** Vink Details' privacy model. The paused draft implemented what it
  believed was Phase 4 §11's "widening" — every participant's own name, amount, and outcome
  visible to every other participant and the organizer alike. The owner corrected this before
  ship (**D43**): the organizer sees only a customer-safe aggregate; a participant sees only
  their own share/outcome. The backend query, the Dart models, the screen widget, and every
  test referencing the old shape were rewritten, not patched.

## Home hierarchy

Signed-in Home now renders, top to bottom: a restrained header (wordmark + Profile icon, no
tagline, no greeting), the "Start a Vink" action, then — flag on — two labeled sections ("Needs
your attention" first, "Waiting on others" second; a section header only renders when it has at
least one card), then a plain "See Activity" link. Terminal Vinks (`COMPLETED`/`CANCELLED`/
`EXPIRED`) are excluded from both sections (`_isActive`/`_terminalStates`, provider-level).

## Tagline removal

The persistent "Everyone In. One Payment." heading and the "Hi, $firstName" greeting are both
gone, unconditionally (not gated behind `homeActivityV2` — this reflects the R0 decision
itself, so keeping either on the old flow while removing it from the new one would contradict
the decision). Not replaced with any generic greeting or promotional sentence, per the brief's
own explicit instruction — just the identity mark and Profile access.

## Organizer/participant role treatment

Each active-Vink card shows a plain-text role label ("Organizer"/"Participant") under the
title — not a colored pill, per this slice's own "avoid excessive status pills" visual
direction. Attention-bucket classification differs by role: RESTRICTED is `needsAttention` for
the organizer (the recovery ladder needs them) but `waitingOnOthers` for a participant (D24/D25's
"already settled by the time RESTRICTED is reachable" rule) — this is the one place the two
roles' classification genuinely diverges, and it's covered by 11 direct unit tests
(`attention_bucket_test.dart`).

## Activity resilience

Both `recentActivityProvider` (old, flag-off) and `vinkOutcomesProvider` (new, flag-on) fetch
per-vink inside a try/catch; a failing vink is skipped, not fatal — the provider returns
`{items/summaries, failedCount}` and the screen renders an honest "N Vink(s) couldn't load
right now" banner above whatever did load successfully. Proven at both the provider level
(`activity_providers_test.dart`, a fake repository that fails specific vink ids) and the widget
level (`activity_screen_test.dart`, both flag states).

## Vink Details: organizer/participant privacy (D43)

The organizer's view: purpose/category title, total, an aggregate summary line ("$X confirmed ·
N of M paid"), an unconditional "You organized this Vink" line with no further detail,
timeline, and a conditional support link. Never a participant's name, amount, or status —
verified by asserting the fixture's own participant display name (`'Org'` in the widget test,
`'Member B'` in the backend test) never appears in the rendered output or the serialized JSON
response, respectively.

The participant's view: the same purpose/total/aggregate/timeline/support-link scaffold, plus a
"Your share" section — the organizer's identity, the viewer's own assigned share, and the
viewer's own outcome. Never another participant's data (there is none on this screen to leak by
construction — the server-side query never includes it in the response at all, not merely
hidden client-side).

Both views preserve the pre-existing D31 regression (`textContaining('eceipt')` findsNothing in
every state, including the recovery-required/support-link path) and D29's routing (Activity's
row tap navigates to `/activity/:vinkId`).

## Mobbin patterns adopted/adapted/rejected

Per the R0-completed reference pack and its own owner-ratified Adopt/Adapt/Reject findings,
applied here: amount/purpose hierarchy over dense cards (each card leads with title/amount, not
a stat grid); compact rows over repeated shadows/nested cards (`VinkSurfaceCard` used flat, no
elevation stacking); explicit text outcomes rather than color-only status (every card/row/detail
screen states its outcome in words — `_outcomeCopy`, `_outcomeStatement` — never relies on badge
color alone, directly tested in the new accessibility-label test); low-alarm, record-scoped
support links (the "Contact support" affordance only appears when the specific Vink's own
outcome is unclear, never a blanket help button); progressive disclosure (Vink Details shows the
aggregate first, role-specific detail second, timeline third). Rejected outright: generic
fintech dashboard summaries, excessive status pills, Cash App's ambiguous pending-state
treatment, Splitwise debt-ledger language — none of these appear anywhere in the shipped copy or
layout.

## Data limitations

- **No per-day Activity totals, no combined feed** — both explicitly excluded per R0; verified
  by direct regression tests (`activity_screen_test.dart`'s "no per-day or overall spending
  total" test, `home_screen_test.dart`'s "never renders a raw activity feed" test).
- **The "$90 of $120, 3 of 4 paid" progress moment** (D19, flagged in PV13-SCREENSHOTS.md)
  remains unreachable — `fundedAmountMinor` still only moves atomically at full resolution
  (D5). Home's compact bar now correctly sources `contributionProgress`'s own incremental
  fields (`confirmedAmountMinor`/`confirmedParticipantCount`), which — unlike
  `fundedAmountMinor` — genuinely do update per-contribution, so this slice narrows but does not
  fully close D19's gap; the funding-progression visual moment itself is unaffected by this
  slice (no settlement-semantics change was made).

## Real-device result

Two runs on a real booted iOS Simulator ("iPhone 17 Pro") against the real local backend
(Postgres 16 + Redis, `apps/api/src/server.ts` with `VINKIN_PARTICIPANT_INCLUSIVE_RETRIEVAL=1`
and the documented CORS env vars):

1. **`e1_test.dart` (regression, flag off)** — the full $120 organizer journey, re-verified
   clean after the Home greeting removal (the one assertion that needed updating) and the
   `VinkSnapshot`/`ContributionProgress` model changes.
2. **`i6_home_activity_details_test.dart` (new, `--dart-define=HOME_ACTIVITY_V2=true`)** — one
   continuous real journey: an organizer creates and opens a $60 Vink, pays their own share,
   sees it under "Waiting on others" with the "Organizer" role label; Activity shows nothing
   for it yet (not terminal); the member's payment and the merchant simulation are driven
   directly against the API (matching this codebase's established pattern for the non-UI half
   of a journey); once COMPLETED, Home excludes the Vink and Activity shows its outcome row;
   tapping into Vink Details confirms the aggregate-only organizer view ("You organized this
   Vink", "2 of 2 paid", the member's real display name absent, no "receipt" language anywhere).
   The test then signs out and back in as the member: Activity shows the same completed Vink;
   Vink Details shows the own-data-only participant view ("Organized by I6 Organizer", no "You
   organized this Vink" text). Finally, the same account creates a second, still-open Vink as
   organizer (with a guest — a solo Vink is rejected client-side, a real product rule this test
   surfaced): Home renders the new organizer-role card, and Activity — now holding both a
   terminal participant-role entry and an active organizer-role Vink — renders without
   crashing, closing the loop on the mixed-role requirement.

One real environment defect surfaced and fixed along the way, not new code: the local disk
filled to 98% (267Mi free) mid-session — the same recurring class of environment cruft prior
milestones have documented (ENG1-TIMER-SEMANTICS.md, ENG1-SLICE-3). Freed with the owner's
explicit approval: Xcode DerivedData (450M) and `pnpm store prune` (518M), both pure,
regenerable build caches — no project files touched. The disk fill had also silently pushed
Redis into `stop-writes-on-bgsave-error`, which manifested as the API server's BullMQ sweep
queue throwing on every poll; resolved by freeing space and issuing a manual `BGSAVE` before
restarting the server.

## Deviations

- **The Vink Details privacy model shipped opposite to this slice's own first-pass
  implementation** — see D43. This is the one substantive deviation from the paused working
  tree, made deliberately and disclosed, not silently patched over.
- **`VinkSnapshot.contributionProgress` is now a required field** — the server always sent it
  (D20/D24); the Dart model simply hadn't parsed it before this slice. This surfaced two other
  test files (`canonical_create_vink_screen_test.dart`, `router_flag_test.dart`) hand-
  constructing raw snapshot JSON without it; both fixed as a direct, disclosed consequence of
  the model change, not a separate unrelated fix.
- **The mixed-role real-device proof required adding a second participant** — a solo
  (organizer-only) Vink is rejected client-side ("Add at least one other person before
  continuing."), a real, previously-undocumented-in-this-slice product rule the test itself
  surfaced; the test was adjusted to add a guest rather than treated as a bug, since nothing in
  the brief asked for solo-Vink support.

## Is I6 fully closed?

Yes. All three screens (Home, Activity, Vink Details) are rebuilt per the brief and the R0
decisions; the D43 privacy correction is implemented, tested at both the backend-leak and
widget-absence level, and documented; every required test category from the brief exists and
passes; real-device verification covers all three named flows (organizer, participant, mixed-
role); full repo-wide validation is green modulo the two independently-confirmed pre-existing/
unrelated gaps (`apps/guest-web`'s Slice I3/I3A tests, the one flaky heartbeat test under
parallel load). No further I6 work is planned — per the brief's own "Stop after I6."
